### 3. 현재 코드에서 반드시 확인할 문제

다음은 사전 분석에서 발견한 핵심 위험이다. 실제 줄 번호가 달라질 수 있으므로 함수·변수 이름으로 다시 확인하고, 확인 결과를 변경 전 보고서에 남겨라.

1. 중앙 서버의 `_four_abb_start_sent`는 프로세스 메모리에만 존재하며, `sendall()` 호출 뒤 `True`가 된다. ABB/RAPID만 재시작하면 이 값이 남아 있어 필요한 `Start`가 다시 전송되지 않을 수 있다.
2. `Server_admin_Web.py`의 생산 시작부는 AMR, 3abb, 5abb로 명령을 연속 전송하지만 모든 `send()` 결과와 실제 수신·실행 확인을 강제하지 않는다.
3. 중계기는 ABB와 중앙 서버 연결을 독립 상태로 관리하지 못하고, 한쪽 재접속 과정이 다른 쪽의 상태 판단에 영향을 줄 수 있다.
4. `3abb_connector.py` 계열은 ABB 전송 실패 뒤 연결을 복구하고 같은 명령을 자동 재전송한다. 첫 전송이 ABB에 도착했는지 불확실한 경우 `Start` 같은 명령이 중복 실행될 수 있다.
5. RAPID의 `Run_Socket_Server`와 `Start_Server`는 통신 세션 재생성과 업무 상태를 강하게 결합한다.
6. RAPID의 `WaitForAmrArrived`가 외부 명령 수신 루프와 같은 소켓에 대해 별도의 `SocketReceive`를 수행한다. 수신 책임자가 둘이 되어 예상하지 않은 메시지를 소비할 가능성이 있다.
7. 현재 중앙 서버의 `connected`는 TCP 소켓이 붙었다는 뜻에 가깝고, 중계기 뒤의 ABB/RAPID가 실제 명령 수신 가능하다는 뜻은 아니다.
8. 세션 ID, 명령 ID, 명시적 ACK/RESULT, heartbeat 만료 시간, 재접속 후 상태 동기화가 충분하지 않다.

### 4. 필수 설계 원칙

#### 4.1 연결과 준비 상태를 분리

각 구성 요소 상태를 최소한 다음처럼 관리하라.

`DISCONNECTED → CONNECTING → TCP_CONNECTED → HANDSHAKING → SYNCHRONIZING → READY → BUSY → READY`

예외 상태로 `DEGRADED`, `RECONNECTING`, `RECOVERY_REQUIRED`, `FAULT`를 지원하라. 중앙 서버는 `TCP_CONNECTED`만으로 명령을 보내지 말고, 해당 장치가 현재 세션에서 `READY`임이 확인된 경우에만 작업 명령을 허용하라.

#### 4.2 세션 기반 핸드셰이크

연결할 때마다 새 세션 식별자를 생성하라.

- `server_session_id`: 중앙 서버 프로세스가 시작될 때 생성
- `relay_session_id`: 각 중계기 프로세스가 시작될 때 생성
- `robot_session_id`: RAPID 메인 또는 통신 태스크가 시작될 때 생성 가능한 범위에서 구현. RAPID 제약 때문에 UUID가 어렵다면 부팅 카운터·시간·난수 조합 또는 중계기가 새 ABB 연결마다 부여한 식별자를 사용하고 그 한계를 문서화

최소 핸드셰이크 흐름:

```text
relay -> central : HELLO relay=3abb protocol=2 relay_session=R-81
central -> relay : WELCOME protocol=2 server_session=S-15
relay -> central : ROBOT_STATUS robot_session=A-42 state=IDLE last_command=cmd-100
central -> relay : SYNC_REQUEST desired_run=none
relay -> central : READY robot_session=A-42 state=IDLE
```

기존 단순 문자열 프로토콜과 단계적으로 공존해야 한다면 `protocol=1` 호환 모드와 `protocol=2` 신뢰성 모드를 명시적으로 나누고, 호환 모드에서는 웹 UI에 `LEGACY / readiness 미검증` 경고를 표시하라.

#### 4.3 Desired State와 Observed State

중앙 서버가 원하는 상태와 장비가 보고한 실제 상태를 별도로 저장하라.

- Desired State 예: `receiving_enabled=true`, `desired_run_id=run-7`
- Observed State 예: `robot_session=A-42`, `state=WAITING_PLC`, `last_completed_command=cmd-102`

`_four_abb_start_sent` 같은 영구적인 불리언은 제거하거나 반드시 `robot_session_id`에 귀속하라. ABB/RAPID의 새 세션이 관측되면 이전 세션의 `Start 전송됨`, `READY`, `BUSY`, 대기 이벤트를 모두 무효화하고 재동기화하라.

#### 4.4 명령 생명주기

작업 명령에는 최소한 다음 필드를 포함하라.

```text
COMMAND run_id=run-7 command_id=cmd-103 expected_state=IDLE action=START
ACK command_id=cmd-103 status=ACCEPTED
EVENT command_id=cmd-103 status=STARTED
RESULT command_id=cmd-103 status=COMPLETED
```

- `sendall()` 성공은 완료가 아니라 `운영체제 송신 버퍼에 쓰기 성공`으로만 취급하라.
- 중앙 서버는 ACK·RESULT의 타임아웃과 오류를 명시적으로 처리하라.
- `run_id`가 다른 과거 `Done`, `ConveyDone`, `ReadyForPickup` 메시지는 현재 작업 완료로 인정하지 말라.
- 명령 처리 결과를 웹 로그에 `run_id`, `command_id`, `session_id`와 함께 표시하라.

#### 4.5 중복 방지와 재전송 안전성

- `START`, `RESET`, 로봇 동작, 컨베이어 동작은 자동 재전송 금지 명령으로 분류하라.
- 전송 결과가 불확실하면 `RECOVERY_REQUIRED`로 전환하고 장비 상태를 조회·동기화한 뒤 결정하라.
- 동일 `command_id`를 다시 받으면 RAPID 또는 중계기는 동작을 두 번 수행하지 않고 기존 ACK/RESULT를 되돌려주는 멱등 처리를 구현하라.
- RAPID에서 영속 저장이 현실적으로 어렵다면 중계기 SQLite에 `robot_session_id + command_id + result`를 저장하되, ABB 새 세션에서는 안전하게 무효화 또는 재검증하라.

#### 4.6 독립적인 연결 감독기

각 중계기는 다음 두 연결을 독립적인 루프 또는 스레드로 관리하라.

- `central_supervisor`: 중앙 서버 연결·재연결·핸드셰이크·heartbeat
- `robot_supervisor`: ABB 연결·재연결·상태 조회·heartbeat

한쪽이 끊어져도 다른 쪽 감독기가 멈추지 않아야 한다. 상태 조합은 다음처럼 보고하라.

- 중앙 연결 O, ABB 연결 X → `DEGRADED / ROBOT_OFFLINE`
- 중앙 연결 X, ABB 연결 O → ABB 연결을 유지하되 새로운 동작 명령을 실행하지 않음
- 둘 다 O, 핸드셰이크 미완료 → `SYNCHRONIZING`
- 둘 다 O, 세션과 상태 확인 완료 → `READY`

명령 큐에는 최대 크기와 만료 시간을 두라. 로봇이 오프라인일 때 들어온 동작 명령은 쌓아 두었다가 나중에 실행하지 말고 즉시 `REJECTED ROBOT_NOT_READY`로 응답하라.

#### 4.7 Heartbeat와 만료

- 중앙↔중계기, 가능하면 중계기↔ABB 모두 heartbeat를 추가하라.
- 권장 초기값: 2초 주기, 6초 TTL. 설정으로 변경 가능하게 하라.
- TTL이 지나면 소켓 객체가 남아 있어도 `READY`를 취소하고 `DEGRADED` 또는 `DISCONNECTED`로 전환하라.
- 재연결은 지수 백오프와 작은 jitter를 사용하되, 장시간 끊겨도 자동 복구를 계속 시도하라.

#### 4.8 RAPID 수신 책임 단일화

- 하나의 클라이언트 세션에서는 한 곳만 `SocketReceive`를 호출하도록 구조를 바꿔라.
- `WaitForAmrArrived` 같은 업무 함수가 직접 소켓을 읽지 않도록 하고, 중앙 수신 루프가 파싱한 이벤트를 RAPID 상태 변수·큐·플래그에 전달하라.
- listener socket과 client socket의 생명주기를 분리하여 클라이언트 단절 시 listener 전체를 불필요하게 재생성하지 않도록 하라.
- 통신 오류가 로봇 업무 상태를 임의로 초기화하거나, 반대로 업무 함수가 통신 수신을 독점하지 않도록 하라.
- RobotWare 옵션과 현재 프로젝트 제약을 확인한 뒤, 가능하면 통신 태스크와 로봇 모션 태스크 분리를 검토하라. 멀티태스킹 옵션이 없으면 단일 태스크 내 비차단 상태 머신으로 구현하고 한계를 문서화하라.

### 5. 중앙 서버의 준비 장벽

생산 시작 버튼을 눌렀을 때 다음 모든 조건이 충족되어야 실제 시작을 허용하라.

- AMR: 현재 세션에서 `READY`
- 3abb: 중계기와 ABB 모두 현재 세션에서 `READY`
- 4abb: 중계기와 ABB 모두 현재 세션에서 `READY`이며 필요한 수신 상태가 관측됨
- 5abb: 중계기와 ABB 모두 현재 세션에서 `READY`
- 진행 중인 다른 `run_id` 없음
- 해결되지 않은 `RECOVERY_REQUIRED` 없음

조건 미충족 시 전송을 일부만 수행하지 말고 생산 시작 전체를 거부하라. 웹 UI에는 어떤 구성 요소의 어떤 조건이 부족한지 표시하라. 모든 `send()`·ACK·RESULT의 반환을 검사하고, 실패를 무시하지 말라.

### 6. 영속 상태와 로그

Python 표준 라이브러리 `sqlite3`를 우선 사용하여 다음을 저장하라.

- 세션 시작·종료
- 명령과 상태 전이
- ACK·RESULT
- 현재/최근 `run_id`
- unresolved command 또는 `RECOVERY_REQUIRED`

프로세스 재시작 후 DB 내용만 믿고 작업을 재개하지 말고, 항상 현재 장비 세션과 관측 상태를 다시 조회한 뒤 조정하라. 로그에는 사람이 읽기 쉬운 메시지와 구조화 필드가 함께 있어야 한다.

### 8. 필수 자동 테스트

실제 장비 없이 가짜 중앙 서버·가짜 중계기·가짜 ABB 소켓을 사용해 최소한 다음을 자동화하라.

1. 가능한 모든 최초 기동 순서가 최종 `READY`로 수렴
2. 중앙 서버 단독 재시작 후 새 `server_session_id`로 재동기화
3. 중계기 단독 재시작 후 이전 relay 세션 무효화
4. ABB 단독 재시작 후 이전 `_four_abb_start_sent` 성격의 상태 무효화
5. ABB 오프라인 상태에서 `Start`가 버퍼링되지 않고 거부됨
6. 전송 직후 연결 단절로 결과가 불확실할 때 자동 재실행하지 않고 `RECOVERY_REQUIRED`
7. 같은 `command_id`를 두 번 보내도 동작은 한 번만 실행
8. 이전 `run_id`의 늦은 `Done`이 현재 생산 완료로 처리되지 않음
9. heartbeat TTL 만료 시 `READY` 해제
10. 네트워크 복구 후 핸드셰이크·상태 동기화를 거쳐 다시 `READY`
11. 잘린 패킷, 한 번에 여러 줄 수신, UTF-8 오류, 알 수 없는 명령, 너무 긴 메시지 처리
12. 명령 큐 최대 크기와 만료 시간 동작

기동 순서 테스트 결과는 표로 정리하라. Python 코드는 `py_compile` 및 프로젝트 테스트를 통과해야 한다. RAPID 코드는 RobotStudio에서 검증해야 할 항목을 체크리스트로 제공하고, 가능한 정적 검사를 수행하라.

### 9. 완료 조건

다음이 모두 충족되어야 완료로 보고하라.

- 특정 기동 순서를 요구하는 코드 경로가 제거되었거나 명시적인 세션 동기화로 대체됨
- TCP 연결과 실제 준비 상태가 UI·코드·로그에서 구분됨
- ABB/RAPID 재시작 시 이전 세션의 플래그와 이벤트가 남지 않음
- 위험 명령은 불확실한 상태에서 자동 재전송되지 않음
- 생산 시작은 전 구성 요소 readiness barrier를 통과해야 함
- 모든 명령이 `run_id`, `command_id`, `session_id`로 추적됨
- 자동 테스트가 기동 순서·재시작·중복·단절 시나리오를 검증함
- 기존 기능 회귀 여부와 남은 위험을 문서화함

### 10. 최종 보고 형식

마지막 답변은 다음 순서로 작성하라.

1. 구현 결과 한 문단 요약
2. 변경된 파일 목록과 핵심 변경
3. 변경 전·후 구조 비교
4. 실행한 테스트와 결과
5. RobotStudio/실장비에서 사용자가 검증할 체크리스트
6. 남은 위험과 다음 권장 작업

실패나 미완료 항목이 있으면 완료로 표현하지 말고, 정확한 파일·함수·오류와 재현 방법을 적어라.

## 이 프롬프트의 핵심 판단 기준

좋은 결과는 단순히 재접속을 무한 반복하는 코드가 아니다. 모든 프로그램이 서로 다른 시간에 켜져도 현재 세션의 실제 상태를 교환하고, 안전하게 `READY`로 수렴하며, 결과가 불확실한 로봇 명령을 자동으로 다시 실행하지 않는 구조여야 한다.
