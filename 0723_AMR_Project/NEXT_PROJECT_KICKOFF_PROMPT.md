# 차기 프로젝트 킥오프 프롬프트 — "자동차 조립 자동화 공정" PLC+ABB+AMR 시스템 (v2)

이 문서는 `0723_AMR_Project`(1차: 3abb/5abb/4abb ABB 로봇 + Omron LD-90 AMR + 중앙
Python 서버 + PLC 연동) 프로젝트를 진행하며 실제로 부딪혔던 문제와 그 해결 과정을
정리한 것입니다. **다음 프로젝트는 같은 주제(자동차 조립 자동화 공정 시연)를 더
고도화해서 처음부터 새로 만드는 것**이고, 이 문서는 새 프로젝트를 시작할 때
AI에게 그대로 붙여넣을 "킥오트 프롬프트"로 쓰기 위한 것입니다. 기존 코드를
이어받는 게 아니라, **기존에 겪었던 실수를 반복하지 않기 위한 체크리스트**로
활용하는 게 목적입니다.

---

## 1. 프로젝트 개요 (배경)

- ABB 로봇 3대(3abb, 5abb: 상/하부 차체 조립 및 출고 / 4abb: 부품 수신)와
  Omron LD-90 AMR(Arduino UNO R4 WiFi로 브릿지), 중앙 Python 관리 서버, PLC가
  TCP 소켓으로 서로 연동되어 "자동차 조립 자동화 공정"을 시연하는 프로젝트였음.
- 핵심 요구사항: 각 조립 스테이션(3abb/5abb)은 완성품을 **AMR이 실제로 픽업하러
  도착했다는 게 확인된 뒤에만** 출고 컨베이어를 가동해야 함. AMR이 없는데 먼저
  출고되면 안 됨.
- 아키텍처: RAPID(로봇)이 자체 TCP 소켓 서버를 열고, 로봇 옆 노트북에서 도는
  Python "중계기"가 로봇 소켓 ↔ 중앙 관리 서버 사이를 릴레이. AMR(아두이노)은
  자율적으로 여러 스테이션을 순회하며 자신의 진행 상황을 STATUS/EVENT 로그로
  중앙 서버에 보고. 중앙 서버가 "ReadyForPickup"(로봇→서버)과 AMR의 도착 신호
  (AMR→서버)를 매칭해서 "AmrArrived"(서버→로봇)를 내려주는 방식으로 게이팅.

**이 아키텍처 패턴 자체는 잘 동작했고, 다음 프로젝트에서도 기본 골격으로 다시
써도 좋다고 판단됨** — 문제는 아키텍처가 아니라 아래 정리한 세부 실수들이었음.

## 2. 가장 크고 중요한 교훈 — 소프트웨어와 물리(PLC) 배선의 불일치

**최종적으로 몇 주간의 "왜 AMR 없는데 출고되지?" 버그의 진짜 원인은 코드가
아니라 PLC 배선이었습니다.** 완성품을 팔레트에 올려놓았다는 확인 신호
(`do05_Body_Docking_Done`)를, 배선 제약 때문에 PLC 쪽에서 **그대로 출고
컨베이어 기동 트리거로도 같이 썼던 것**이 원인이었습니다. RAPID/서버 로그는
매번 완벽하게 정상으로 찍혔는데(AMR 도착 확인 로직 자체는 실제로 문제없었음),
정작 물리적인 컨베이어는 그 소프트웨어 게이팅과 무관하게 "도킹 완료" 신호 하나만
보고 바로 돌아갔던 것입니다.

**이걸 찾기까지 정말 오래 걸렸던 이유**: 소프트웨어 로그만 계속 파봐서는
절대 안 보이는 종류의 버그였음. 시뮬레이션 테스트도 다 통과했음(소프트웨어
로직 자체는 진짜로 옳았으니까). 결국 사용자가 직접 "이거 배선 문제 때문에
그냥 도킹완료 신호를 출고 신호로 쓰기로 했었다"고 말해줘서야 풀림.

### 다음 프로젝트에서 반드시 지킬 것

1. **"확인/완료" 신호와 "허가/실행" 신호를 처음부터 물리적으로 분리해서
   설계하고, 각각 별도의 DO로 배선한다.** 배선 핀이 모자라거나 급하다고
   하나를 겸용으로 쓰지 않는다. 겸용으로 써야만 하는 상황이 생기면, **그
   사실을 코드 주석이 아니라 배선도/I-O 매핑 문서에 명시적으로 남기고,
   RAPID 쪽에서 그 신호를 쏘는 위치도 반드시 "허가 조건을 통과한 뒤"로
   맞춘다.**
2. **모든 DI/DO는 "이 신호를 PLC/외부 장비가 실제로 무엇의 트리거로 쓰는지"를
   코드 주석이 아니라 별도의 I/O 매핑 문서(스프레드시트 등)에 기록**하고,
   RAPID를 수정하는 사람과 PLC 래더를 수정하는 사람이 같은 문서를 본다.
   AI(저)는 배선도를 볼 수 없어서, 코드만 봐서는 이런 종류의 버그를 원천적으로
   못 찾습니다 — 사람이 "이 신호 실제로 뭐에 연결되어 있어요?"를 먼저 물어봐
   줘야 함.
3. "소프트웨어 로그는 완벽히 정상인데 물리적으로는 계속 이상하다"는 증상이
   보이면, **처음부터 "이 결과를 만드는 물리적 신호가 소프트웨어가 의도한
   신호와 정말 같은 신호인가?"를 최우선으로 의심한다.** 몇 주씩 코드만 다시
   읽는 것보다 배선도 한 번 확인하는 게 빠름.

## 3. 실제로 겪은 버그/실수 목록 (같은 실수 반복 방지용)

### 3.1 RAPID FOR 루프 카운터를 다른 PROC에서 그대로 읽으면 안 됨
루프 변수(`FOR n FROM 1 TO 2 DO ... ENDFOR`)를 선언한 PROC이 아닌 **다른
PROC에서 그 변수를 그대로 읽으면 실측 기준으로 신뢰할 수 없었음** (실제
로봇이 2번째 반복에서도 1번 위치로 감 — 로봇을 직접 관찰해서 확인된 버그).
**해결**: 값을 파라미터로 명시적으로 넘겨서 씀 (`Lower_Body(num pickIndex)`
형태). → 다음 프로젝트: 루프 카운터가 필요한 다른 PROC이 있으면 처음부터
파라미터로 넘기는 패턴으로 설계.

### 3.2 SocketSend는 줄바꿈을 자동으로 안 붙임
RAPID `SocketSend`는 `\0D\0A`를 명시적으로 안 붙이면 중계기가 한 줄로 못
읽고 다음 메시지와 합쳐져서 깨진 메시지가 됨. 이 문제가 **"Done"**,
**"ReadyForPickup"**, **커스텀 상태 메시지** 등 여러 군데서 각각 따로 발견됨
(한 번 고치고 끝난 게 아니라 계속 재발). → 다음 프로젝트: 모든 SocketSend를
감싸는 공용 PROC(`SendLine(string msg)` 같은 걸 만들어서 항상 `\0D\0A`를
붙이도록 강제 — 개별적으로 매번 챙기지 않게.

### 3.3 중계기(relay) 버퍼 드레인은 양방향 다 필요함
"한 번의 recv()에 여러 줄이 섞여 들어올 수 있다"는 문제를, **로봇→서버
방향만 먼저 고치고 서버→로봇 방향은 나중에 따로 또 발견**됨. → 다음
프로젝트: 중계기를 처음 설계할 때부터 양방향 다 동일한 드레인 루프를
적용.

### 3.4 "픽업하러 옴"과 "그냥 지나가며 반납/전달하러 옴"을 프로토콜 레벨에서
   명확히 구분해야 함
AMR이 한 스테이션에 여러 목적(싣기/반납/단순 경유)으로 여러 번 들를 수
있는데, 방향(FWD/REV)이나 목적을 구분하지 않고 "도착했다"는 이벤트 하나로만
처리하면, 반납하러 온 것도 "픽업 도착"으로 오인될 위험이 있음(실제로 이
설계 실수가 프로젝트 초기 버전 서버 코드에 있었던 걸 확인함). → 다음
프로젝트: 처음부터 이벤트 이름 자체를 목적별로 분리 (`PICKUP_ARRIVED` /
`RETURN_ARRIVED` / `TRANSFER_ARRIVED`처럼) — 나중에 리팩터링하지 말고
처음부터.

### 3.5 센서 기반 완료 판정은 "지금 감지됨"이 아니라 "꺼졌다가 다시 켜짐"을
   요구해야 함
어떤 스테이션의 재적재 로직은 "센서가 먼저 꺼진 뒤 다시 감지되는" 새 신호만
인정하도록 보호되어 있었는데, 다른(구조적으로 동일한) 로직엔 이 보호가
빠져 있었음 — 이전 물체의 잔류 감지가 새 감지로 오인될 수 있는 비대칭.
→ 다음 프로젝트: "센서로 완료를 판정하는" 모든 곳에 동일한 fresh-edge
정책을 처음부터 통일 적용.

### 3.6 AMR 경로 중단(장애물 등) 처리 정책을 미리 설계해둘 것
실제 운영 중 AMR의 ARCL 패트롤이 종종 중단됨(`Interrupted: Patrolling
route...`). 초기엔 이걸 바로 실패 처리해서 전체 시퀀스가 멈췄고, 나중엔
"자재 이동이 시작되기 전 구간에서만, 최대 N회, M초 간격으로 자동 재시도"로
개선함. → 다음 프로젝트: 이 정책(어디까지 재시도 허용, 몇 번, 실패 시 어떻게
알릴지)을 처음부터 설계해두고 시작. 특히 **컨베이어/자재 이동이 이미
시작된 뒤에는 재시도하면 안 됨**(중복 동작 위험) — 이 경계선을 명확히.

### 3.7 서버 오케스트레이션에서 타임아웃 없는 블로킹 대기 금지
`threading.Event().wait()`처럼 타임아웃 없이 무한정 기다리는 코드가 있으면,
그 신호 하나가 안 오는 순간 전체 자동 생산 스레드가 조용히 멈춰버림(겉보기엔
"서버가 아직 살아있는" 것처럼 보이지만 실제로는 멈춘 상태) . → 다음
프로젝트: 모든 대기는 짧은 타임아웃으로 폴링 + 실패/중단 상태를 감지할 수
있는 별도 플래그와 함께 설계.

### 3.8 배포 버전 불일치가 "유령 버그"의 최대 원인이었음
프로젝트 내내 반복된 패턴: **실제 로봇/AMR에 올라간 코드가 저장소의 최신
코드보다 오래된 버전**이었거나, **서로 다른 세션(AI)이 독립적으로 만든 두
갈래의 서버/펌웨어**가 뒤섞여서 실행되고 있었음. 코드를 아무리 다시 읽어도
못 찾는 버그였는데, 실제로는 "그 버전이 아예 실행되고 있지 않았던" 경우가
대부분. → 다음 프로젝트:
- 모든 컴포넌트(RAPID 프로그램, 중계기, 중앙 서버, AMR 펌웨어)가 **자기
  버전 문자열을 접속/부팅 시 항상 보고**하게 만들고, 중앙 서버가 화면에
  "기대하는 버전과 다름"을 눈에 띄게 표시.
- **여러 사람/여러 AI 세션이 같은 프로젝트를 독립적으로 건드리는 상황을
  피하고, 버전 관리 주체를 하나로 명확히 정한다.** (이번 프로젝트도
  결국 "이제부터는 한쪽만 버전 관리"로 정리하고 나서야 안정됐음.)
- 문제가 재발하면 "코드가 틀렸나?"보다 **"지금 실제로 그 코드가 돌고
  있는 게 맞나?"를 먼저 확인**하는 습관.

### 3.9 WaitDI 타임아웃 정책은 신호별로 미리 정해둘 것
PLC 신호를 기다리는 `WaitDI`에 타임아웃을 걸지 안 걸지가 신호마다 달라야
했음 — 어떤 신호(예: 프레스 완료)는 "20초 기다리고 안 오면 그냥 넘어가도
안전", 어떤 신호(예: 바디 도킹)는 "안 오면 절대 넘어가면 안 됨(사고
위험)". 이걸 즉흥적으로 하나씩 고치다 보니 일관성이 깨진 적 있었음. → 다음
프로젝트: PLC 담당자와 함께 **신호별로 "타임아웃 허용 여부/시간"을 표로
미리 정의**하고 시작.

## 4. 잘 됐던 것 — 계속 가져갈 것

- **번호(unit=/cycle=/run=) 명시적 태깅**: "몇 번째 차량"인지를 RAPID→서버,
  서버→AMR, AMR→서버까지 전 구간에 숫자로 실어서 순서 매칭뿐 아니라 명시적
  비교까지 가능하게 한 패턴은 디버깅에 실제로 큰 도움이 됐음. 처음부터
  전 구간에 적용할 것.
- **원인 원문 그대로 로깅**: "이 판단(예: 출고 허가)을 왜 내렸는지"를
  판단 시점에 원본 메시지까지 같은 로그 줄에 남기는 패턴 — 나중에 실제
  로그만 보고도 원인을 확정할 수 있었음. 처음부터 이렇게 로깅 설계.
- **실제 프로토콜을 그대로 흉내낸 시뮬레이션 테스트**: 가짜 로봇/AMR
  TCP 서버로 진짜 프로토콜 문자열까지 똑같이 재현하는 파이썬 테스트
  하네스는 소프트웨어 로직 검증에 실제로 유용했음. 다만 **"소프트웨어
  로직만 검증하는 것"이고 배선/PLC 쪽은 절대 못 잡는다**는 한계를 처음부터
  분명히 인지하고 병행할 것 (2번 항목 참고).
- **버전 관리 원칙(파일을 덮어쓰지 않고 새 버전으로 남기고 diff로
  검증)**: 좋은 습관이었음. 다만 "번들 폴더 + 개별 버전 파일" 이중
  체계가 오히려 혼란(중복 파일 등)을 만든 적 있어서, 다음 프로젝트는 좀 더
  단순한 단일 체계로 시작.
- 실제 운영 로그(타임스탬프 포함)를 보여주는 것이 코드만 다시 읽는 것보다
  훨씬 빨리 문제를 좁혀줬음 — 뭔가 이상하면 "정확히 그 순간의 로그"를
  먼저 확보하는 습관.

## 5. 다음 프로젝트 킥오프 시 먼저 확인/합의할 것

1. 모든 DI/DO의 실제 물리적 트리거 대상을 정리한 I/O 매핑 문서 유무.
2. "확인 신호"와 "실행 허가 신호"가 물리적으로 분리되어 있는지.
3. 버전 관리 주체(사람/AI 세션)를 하나로 고정.
4. 각 컴포넌트가 자기 버전을 보고하는 메커니즘 설계.
5. WaitDI 타임아웃 정책 표(신호별 허용 여부/시간).
6. AMR 경로 실패 시 재시도 정책(어디까지, 몇 번, 실패 시 알림 방법).
7. 서버 오케스트레이션의 모든 대기 지점에 타임아웃 적용 여부.
